# 02. Implementation Plan

Derived from the decisions in [decisions.md](decisions.md). Each stage ends with a verification step and a commit.

## Target repository layout

```
.
├── docker-compose.yml              # publisher (pg-primary) + subscriber (pg-replica)
├── docker/postgres/Dockerfile      # postgres:17 + postgresql-17-cron
├── sql/
│   ├── common/                     # DDL shared by both instances
│   │   ├── 01_schema.sql           # schema ops, extensions
│   │   └── 02_operations.sql       # partitioned ops.operations + partition maintenance function
│   ├── primary/                    # publisher-only objects (mounted into /docker-entrypoint-initdb.d)

│   │   ├── 04_generator.sql
│   │   ├── 05_job_functions.sql
│   │   ├── 06_materialized_view.sql
│   │   ├── 07_seed.sql
│   │   ├── 08_jobs.sql
│   │   └── 09_publication.sql
│   └── replica/
│       ├── 03_jobs.sql             # partition maintenance only
```

`docker-entrypoint-initdb.d` runs files in alphabetical order on first start; common files are mounted into both containers with the same numeric prefixes so ordering stays correct.

## Server configuration (both instances)

| Setting | Value | Why |
|---------|-------|-----|
| `shared_preload_libraries` | `pg_cron` | required by pg_cron |
| `cron.database_name` | `opsdb` | jobs run in the application DB |
| `cron.use_background_workers` | `on` | jobs run as background workers — no libpq connection / password needed |
| `max_worker_processes` | `32` | room for cron workers + logical replication workers |
| `wal_level` | `logical` (primary) | required for logical replication |
| `timezone` | `UTC` | deterministic timestamps / partition bounds |

## Stages

### Stage 0 — Environment
- Dockerfile: `FROM postgres:17` + `apt-get install postgresql-17-cron` (the official image already has the PGDG apt repo).
- Compose: `pg-primary` (port 5433) and `pg-replica` (port 5434), shared network, healthcheck on primary via `pg_isready -h localhost` (TCP becomes available only after init scripts finish → replica's subscription is created only when the publisher is ready). `pg-replica` `depends_on: pg-primary: condition: service_healthy`.
- **Verify:** both containers healthy, `CREATE EXTENSION pg_cron` works.

### Stage 1 — Table T1 (requirement 1)
- `ops.operations` partitioned `BY RANGE (op_date)`:
  - `id bigint GENERATED BY DEFAULT AS IDENTITY`
  - `op_date timestamptz NOT NULL DEFAULT now()`
  - `amount numeric(14,2) NOT NULL CHECK (amount > 0)`
  - `status smallint NOT NULL DEFAULT 0 CHECK (status IN (0,1))`
  - `operation_guid uuid NOT NULL DEFAULT gen_random_uuid()`
  - `message jsonb NOT NULL` + `CHECK`s: object with keys `account_number` (string), `client_id` (number), `operation_type ∈ {online, offline}`
  - `PRIMARY KEY (id, op_date)` (must include partition key; also the replica identity)
  - `UNIQUE (operation_guid, op_date)` (local, for lookups)
  - partial index `(id) WHERE status = 0` — the confirm job only scans pending rows
  - expression index on `((message->>'client_id')::bigint, message->>'operation_type')`
- `ops.ensure_monthly_partitions(p_from date, p_months_ahead int)` — idempotent creation of `operations_yYYYYmMM` partitions + `operations_default`.
- `COMMENT ON` with mapping to the task terms.
- **Verify:** `\d+ ops.operations`, list of partitions, insert routes to the right partition.

### Stage 2 — GUID uniqueness (requirement 3)
- `ops.operation_guid_registry (operation_guid uuid PRIMARY KEY, registered_at timestamptz)`.
- BEFORE INSERT row trigger on `ops.operations` → inserts into registry (duplicate → `unique_violation`).
- FK `ops.operations(operation_guid) → registry`.
- Primary only (the subscriber doesn't have the registry; replication triggers don't fire there by default anyway).
- **Verify:** insert same GUID with a different `op_date` (different partition) → fails.

### Stage 3 — Data generation (requirement 2)
- Helpers: `ops.random_message(client_id)` — deterministic account(s) per client (IBAN-like `UA` + 27 digits derived from `client_id`, 1–3 accounts per client), random type.
- `CALL ops.generate_operations(p_rows => 100000, p_from => now() - interval '4 months', p_to => now(), p_batch => 10000)`:
  - per batch: `INSERT … SELECT … FROM generate_series(…)`, uniform random `op_date` within range, status per D-11, `COMMIT`.
- `ensure_monthly_partitions` is called first so no rows go to `DEFAULT`.
- **Verify:** `count(*) ≥ 100000`, `min/max(op_date)` span ≈ 4 months, per-partition counts, `DEFAULT` empty, status distribution.

### Stage 4 — Insert job every 5 s (requirement 4)
- `ops.insert_random_operation() RETURNS bigint` — one row, `status = 0`, `op_date = now()`.
- `cron.schedule('insert-operation', '5 seconds', 'SELECT ops.insert_random_operation()')`.
- **Verify:** `cron.job_run_details` shows successful runs ~5 s apart; new rows with status 0.

### Stage 5 — Confirm job every 3 s (requirement 5)
- `ops.confirm_operations_by_parity() RETURNS int`:
  - `v_parity := extract(second from now())::int % 2` (seconds of the job's transaction start; since 60 is even, minute-second parity == epoch-second parity);
  - `UPDATE ops.operations SET status = 1 WHERE status = 0 AND id % 2 = v_parity`;
  - returns affected rows; `RAISE LOG` with parity for audit.
- `cron.schedule('confirm-operations', '3 seconds', 'SELECT ops.confirm_operations_by_parity()')`.
- **Verify:** pending rows of the matching parity disappear; job history.

### Stage 6 — Materialized view (requirement 6)
- `ops.client_type_totals` = `SELECT client_id, operation_type, sum(amount), count(*) FROM ops.operations WHERE status = 1 GROUP BY …` + `UNIQUE INDEX (client_id, operation_type)` (needed for `CONCURRENTLY`).
- `ops.mv_refresh_log` — timestamp, rows confirmed, duration (observability).
- AFTER UPDATE OF status, FOR EACH STATEMENT trigger with `REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows`:
  - count rows where old.status = 0 AND new.status = 1 (join by `id, op_date`); if > 0 → `REFRESH MATERIALIZED VIEW CONCURRENTLY` + log row.
- **Risks to check first:** transition tables on a partitioned root; `REFRESH … CONCURRENTLY` inside a trigger seeing own transaction's changes. Fallback if `CONCURRENTLY` is not allowed there: plain `REFRESH` (documented).
- **Verify:** MV totals == live `SELECT … WHERE status = 1` after each job run; refresh log grows only on effective 0→1 updates; a no-op UPDATE doesn't refresh.

### Stage 7 — Replication (requirement 7)
- Primary: role `replicator` (`LOGIN REPLICATION`), `GRANT SELECT` on `ops.operations`, `pg_hba` entry for the replica network; `CREATE PUBLICATION ops_pub FOR TABLE ops.operations WITH (publish_via_partition_root = true)`.
- Replica: same common DDL; `CREATE SUBSCRIPTION ops_sub CONNECTION 'host=pg-primary …' PUBLICATION ops_pub` (initial copy included); partition-maintenance job.
- **Risks to check:** identity column on the subscriber accepting replicated values; DEFAULT partition on the subscriber.
- **Verify:** counts and `sum(amount)` per status match on both sides; a fresh row from the 5-s job and a status flip from the 3-s job appear on the replica within seconds; `pg_stat_subscription`, `pg_replication_slots`.

### Stage 8 — Verification & README
- `verify/` — one script per requirement + `verify/run.ps1`/`run.sh` running all against both containers.
- Root `README.md`: quick start, requirement → object mapping, how to observe jobs/MV/replication.
- `docs/03-implementation-log.md` — what was done per stage, problems hit, deviations from the plan.

## Known limitations (to be documented, not solved)
- MV refresh is a full recomputation — fine for ~100k rows; for large volumes switch to an incrementally maintained summary table (D-08).
- Logical replication doesn't replicate DDL: schema changes must be applied to both sides (partitions are handled independently on each side thanks to `publish_via_partition_root`).
- GUID registry grows with T1; partition retention must also prune the registry.
- `pg_cron` interval jobs don't overlap with themselves; if a run takes longer than its interval the next one waits.
