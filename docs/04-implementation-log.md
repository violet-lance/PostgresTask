### Deviations from the plan

1. **Init runner instead of mounting files straight into `/docker-entrypoint-initdb.d`.**
   The plan assumed mounting the common and role-specific files into the init directory. However, the entrypoint only runs files at the top level of that directory (subdirectories are ignored), and it can't pass `psql` variables. `run-init-sql.sh` (baked into the image) merges `/sql/common/*.sql` and `/sql/${INSTANCE_ROLE}/*.sql`, sorts them **by file name**, and runs each with `ON_ERROR_STOP=1`. It passes `replicator_password`, `primary_host` and `primary_db` as psql variables, so the SQL contains no credentials or hostnames. The SQL folders are bind-mounted read-only, so editing SQL needs no image rebuild (only `docker compose down -v && up`).
2. **`.env.example` + compose defaults instead of a committed `.env`** (refines R-11).
   `docker-compose.yml` uses `${VAR:-default}`, so `docker compose up` works on a fresh clone without any file, and a committed `.env` can't accidentally become the place for real secrets.
3. **Image pinned to `postgres:17.12`** (plan said `postgres:17`): the same minor version the plan-review spike ran on, so the spike results stay valid.

## Stage 1 — Table T1 (requirement 1)

Date: 2026-11-18 · Commit: `feat: partitioned operations table with self-healing partition maintenance (stage 1, req 1)`

### What was done

| File | Content |
|------|---------|
| `sql/common/01_schema.sql` | schema `ops`, extension `pg_cron` |
| `sql/common/02_operations.sql` | `ops.operations` (T1), indexes, jsonb `CHECK`s, `COMMENT ON` mapping to task terms; `ops.create_month_partition()`, `ops.ensure_monthly_partitions()`; initial layout; daily `partition-maintenance` pg_cron job |
| `verify/01_table.sql` | 9 non-destructive checks (run in a rolled-back transaction) |

Table layout (both instances):

| Column | Type | Notes |
|--------|------|-------|
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY` | BY DEFAULT so the subscriber accepts replicated ids |
| `op_date` | `timestamptz` | partition key, `DEFAULT now()` |
| `amount` | `numeric(14,2)` | `CHECK (amount > 0)` |
| `status` | `smallint` | `CHECK (status IN (0,1))`, default 0 |
| `operation_guid` | `uuid` | default `gen_random_uuid()` |
| `message` | `jsonb` | 4 `CHECK`s: object; `account_number` ~ `^UA[0-9]{27}$`; integer `client_id`; `operation_type ∈ {online, offline}` |

Constraints/indexes: `PK (id, op_date)`, `UNIQUE (operation_guid, op_date)`, partial `(id) WHERE status = 0`, expression index `(client_id, operation_type)`.

Initial partitions: `operations_y2026m07` … `operations_y2027m01` (4 months back → 5 calendar months, plus 2 ahead = 7) and `operations_default`.

### Problems found and fixed during implementation

1. **Self-healing via plain DELETE + INSERT would desync logical replication** (not caught in the plan review).
   On the publisher, `DELETE FROM operations_default` is published (via the partition root), but the `INSERT` into a not-yet-attached table is not → the subscriber would lose the rows. Fix: **detach `DEFAULT` first**, move the rows while neither table is attached to `ops.operations` (so no DML is published), then attach both. Everything happens in one transaction, so concurrent writers just wait on the lock. Detach/attach are DDL and are not replicated. → To be re-verified with live replication in Stage 7.
2. **Open cursor vs. DETACH.** A PL/pgSQL `FOR … IN SELECT … FROM operations_default` loop keeps a portal open on `operations_default`, and `DETACH` of a relation in use by the same session fails (`cannot ALTER TABLE … because it is being used by active queries in this session`). Caught while writing the code, before the first run: the month list is now materialised into an array first, then iterated with `FOREACH`.
3. **`AND` evaluation order in `CHECK`s.** SQL doesn't guarantee short-circuit evaluation, so `jsonb_typeof(x) = 'number' AND (x)::bigint > 0` may still evaluate the cast on a string and raise a cast error instead of a `check_violation`. The type guards use `CASE WHEN … THEN … ELSE false END`, and `client_id` is validated by a regex on its text form (no cast at all).

### Additional design detail (beyond the plan)

- `ensure_monthly_partitions()` also creates partitions for **every month found in `DEFAULT`**, not just the configured window. On the subscriber this heals replicated rows older than the subscriber's own initial range (e.g. a replica created months after the primary).
- Partition bounds are computed explicitly in UTC (`::timestamp AT TIME ZONE 'UTC'`), independent of the session `TimeZone`.
- Maintenance is serialised with `pg_advisory_xact_lock` (cron run vs. generator call).

`docker exec -i pg-primary psql -U postgres -d opsdb < verify/01_table.sql` (same for `pg-replica`). **9/9 PASS on both instances:**

 5 | PASS | Invalid jsonb messages are rejected by CHECK constraints                (6 of 6 rejected)

## Stage 2 — GUID uniqueness (requirement 3)

Date: 2026-11-18 · Commit: `feat: global operation_guid uniqueness via registry + composite FK (stage 2, req 3)`

### What was done

| File | Content |
|------|---------|
| `sql/primary/03_guid_registry.sql` | `ops.operation_guid_registry` (`PK (operation_guid)`, `UNIQUE (operation_guid, op_date)`); `BEFORE INSERT` row trigger `operations_register_guid_trg` → `ops.register_operation_guid()`; composite FK `operations_guid_registry_fk (operation_guid, op_date)` |
| `verify/03_guid_uniqueness.sql` | 10 checks, rolled back |

### Implementation decisions

- **No `EXCEPTION` block in the trigger function.** In PL/pgSQL each `BEGIN … EXCEPTION` block is a subtransaction; per-row in a 10k-row generator batch, that means 10k subtransactions per transaction (subxid cache overflow → `pg_subtrans` lookups, a known performance cliff). The native error is already precise: `duplicate key value violates unique constraint "operation_guid_registry_pk"`.
- **Registry rows are not deleted with T1 rows.** The registry means "every GUID ever issued", so a GUID can't be reused after its operation is deleted. Retention must prune the registry explicitly after dropping a partition (the FK enforces that order).
- **Side effect of the composite FK, kept on purpose:** `operation_guid` / `op_date` of an existing operation are effectively immutable (the new pair isn't in the registry). Status updates don't touch FK columns, so PostgreSQL skips the FK check for them, at no cost to the confirm job.

### Verification

`verify/03_guid_uniqueness.sql` on pg-primary — **10/10 PASS**:

```
 1 | PASS | Existing data: no duplicate operation_guid across all partitions
 2 | PASS | Existing data: every T1 row has a matching registry row
 3 | PASS | Registry has PRIMARY KEY (operation_guid)
 4 | PASS | T1 has composite FK (operation_guid, op_date) -> registry
 5 | PASS | Insert registers (guid, op_date) in the registry
 6 | PASS | Same guid in ANOTHER partition is rejected        | duplicate key value violates unique constraint "operation_guid_registry_pk"
 7 | PASS | Same guid with the SAME op_date is rejected       | duplicate key value violates unique constraint "operation_guid_registry_pk"
 8 | PASS | Trigger DISABLED: duplicate guid still rejected by composite FK | ... violates foreign key constraint "operations_guid_registry_fk"
 9 | PASS | operation_guid of an existing operation cannot be changed       | ... violates foreign key constraint "operations_guid_registry_fk"
10 | PASS | Status update (FK columns untouched) works
```

Regression: `verify/01_table.sql` still 10/10 on both instances.

Manual tests:

| Test | Result |
|------|--------|
| **Concurrency:** session A inserts GUID `g` and holds the transaction open for 3 s; session B inserts `g` into another partition 1 s later | B **blocked** on the registry PK index until A committed (18:51:30.56 → 18:51:32.48), then failed with `duplicate key … operation_guid_registry_pk`. One row in T1. Race-free. |
| Self-healed partition (Stage 1 path) on the primary | Gets the cloned `operations_register_guid_trg` trigger and `operations_guid_registry_fk` FK |
| `SET session_replication_role = replica` + duplicate GUID | **Accepted** (2 rows) → see limitation below |

### Known limitation (and a correction to the plan review)

`session_replication_role = replica` disables **all** triggers, including the internal ones that enforce foreign keys. In that mode neither the registry trigger nor the composite FK fires, and a duplicate GUID gets in. The plan review (R-02) wrongly listed this role among the cases the composite FK protects against. It has been corrected there with a note.

Why this is acceptable: setting the role requires superuser, and a superuser can bypass any constraint anyway. The only mechanism that survives the `replica` role is a unique **index**, and PostgreSQL can't build a global unique index across partitions. That is the root cause of the whole requirement. On the subscriber, the apply worker does run in the `replica` role, but it only applies changes that were already validated on the publisher.
