## Coding rules *(R-04)*

- Every object reference is schema-qualified (`ops.…`).
- Every function/procedure declares `SET search_path = ops, pg_catalog`. PostgreSQL 17 builds and refreshes materialized views with a restricted `search_path`, so unqualified references inside functions used by the MV would fail.
- Every script is idempotent where practical (`IF NOT EXISTS`, `CREATE OR REPLACE`).

## Server configuration (both instances)

| Setting | Value | Why |
|---------|-------|-----|
| `shared_preload_libraries` | `pg_cron` | required by pg_cron |
| `cron.database_name` | `opsdb` | jobs run in the application DB |
| `cron.use_background_workers` | `on` | jobs run as background workers, so no libpq connection or password is needed |
| `max_worker_processes` | `32` | room for cron workers + logical replication workers |
| `wal_level` | `logical` (primary) | required for logical replication |
| `timezone` | `UTC` | deterministic timestamps / partition bounds |

## Stages

### Stage 0 — Environment
- `.gitattributes` (LF), `.env` with demo passwords *(R-11)*.
- Dockerfile: `FROM postgres:17` + `apt-get install postgresql-17-cron` (the official image already has the PGDG apt repo).
- Compose: `pg-primary` (port 5433) and `pg-replica` (port 5434), shared network. The primary's healthcheck is `pg_isready -h localhost`; TCP only becomes available after the init scripts finish, so the replica's subscription is created only once the publisher is ready. `pg-replica` has `depends_on: pg-primary: condition: service_healthy`.
- **Verify:** both containers healthy; `CREATE EXTENSION pg_cron` works; `SHOW wal_level` = `logical` on the primary.

### Stage 1 — Table T1 (requirement 1)
- `ops.operations` partitioned `BY RANGE (op_date)`:
  - `id bigint GENERATED BY DEFAULT AS IDENTITY` (BY DEFAULT so the subscriber accepts replicated ids — confirmed in the spike)
  - `op_date timestamptz NOT NULL DEFAULT now()`
  - `amount numeric(14,2) NOT NULL CHECK (amount > 0)`
  - `status smallint NOT NULL DEFAULT 0 CHECK (status IN (0,1))`
  - `operation_guid uuid NOT NULL DEFAULT gen_random_uuid()`
  - `message jsonb NOT NULL` + `CHECK`s: an object with keys `account_number` (string), `client_id` (number), `operation_type ∈ {online, offline}`
  - `PRIMARY KEY (id, op_date)` (must include the partition key; also the replica identity)
  - `UNIQUE (operation_guid, op_date)` (target of the uniqueness scheme, see Stage 2)
  - partial index `(id) WHERE status = 0` — the confirm job only scans pending rows
  - expression index on `((message->>'client_id')::bigint, message->>'operation_type')`
- `ops.ensure_monthly_partitions(p_from date, p_months_ahead int)` — idempotent creation of `operations_yYYYYmMM` partitions + `operations_default`. **Self-healing** *(R-03)*: if `DEFAULT` holds rows for a month being created, then in one transaction it creates the table standalone → moves the rows out of `DEFAULT` → `ATTACH PARTITION`.
- Daily pg_cron job `partition-maintenance` → `ensure_monthly_partitions(current month, 2 ahead)`.
- `COMMENT ON` with the mapping to the task terms.
- **Verify:** `\d+ ops.operations`, partition list, insert routes to the right partition, self-healing test (row in `DEFAULT` → partition created → row moved).

### Stage 2 — GUID uniqueness (requirement 3) *(R-02)*
- `ops.operation_guid_registry (operation_guid uuid PRIMARY KEY, op_date timestamptz NOT NULL, UNIQUE (operation_guid, op_date))`.
- BEFORE INSERT row trigger on `ops.operations` → inserts `(operation_guid, op_date)` into the registry.
- `FOREIGN KEY (operation_guid, op_date) REFERENCES ops.operation_guid_registry (operation_guid, op_date)` — together with the registry PK and T1's `UNIQUE (operation_guid, op_date)` this makes the GUID globally unique **by constraints alone** (proof in the review).
- Primary only. Logical replication applies already-validated changes; the subscriber has no registry.
- **Verify:** inserting the same GUID with a different `op_date` (different partition) fails, both with the trigger enabled and with it disabled.

### Stage 3 — Data generation (requirement 2)
- Helper `ops.make_message(client_id)` — deterministic account(s) per client (IBAN-like `UA` + 27 digits derived from `client_id`, 1–3 accounts per client), random type.
- `CALL ops.generate_operations(p_rows => 100000, p_from => now() - interval '4 months', p_to => now(), p_batch => 10000)`:
  - first `ensure_monthly_partitions(date_trunc('month', p_from), …)`. 4 months back touches 5 calendar months *(R-10)*;
  - per batch: `INSERT … SELECT … FROM generate_series(…)`, uniform random `op_date` within the range, status per D-11, then `COMMIT`.
- **Verify:** `count(*) ≥ 100000`, `min/max(op_date)` span ≈ 4 months, per-partition counts, `DEFAULT` empty, status distribution, GUID registry count == T1 count.

### Stage 4 — Insert job every 5 s (requirement 4)
- `ops.insert_random_operation() RETURNS bigint` — one row, `status = 0`, `op_date = now()`.
- `cron.schedule('insert-operation', '5 seconds', 'SELECT ops.insert_random_operation()')`.
- **Verify:** `cron.job_run_details` shows successful runs ~5 s apart; new rows with status 0.

### Stage 5 — Confirm job every 3 s (requirement 5)
- `ops.confirm_job_log (run_at, run_second, parity, rows_confirmed)` *(R-06)*.
- `ops.confirm_operations_by_parity() RETURNS int`:
  - `v_second := extract(second from now())::int`, `v_parity := v_second % 2`. This is the second of the job's transaction start; since 60 is even, minute-second parity == epoch-second parity *(R-08)*;
  - `UPDATE ops.operations SET status = 1 WHERE status = 0 AND id % 2 = v_parity`. "id" means T1's `id`, not `client_id` *(R-08)*;
  - inserts a row into `confirm_job_log`; returns the affected row count.
- `cron.schedule('confirm-operations', '3 seconds', 'SELECT ops.confirm_operations_by_parity()')`.
- **Verify:** for every logged run, the parity of confirmed ids == logged parity; runs alternate parity; job history.

### Stage 6 — Materialized view (requirement 6)
- `ops.client_type_totals` = `SELECT client_id, operation_type, sum(amount), count(*) FROM ops.operations WHERE status = 1 GROUP BY …` (fully schema-qualified, *R-04*) + `UNIQUE INDEX (client_id, operation_type)` (required for `CONCURRENTLY`).
- `ops.mv_refresh_log` — timestamp, rows flipped 0→1, duration.
- `AFTER UPDATE ON ops.operations REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows FOR EACH STATEMENT`. **No column list:** transition tables are not allowed with `UPDATE OF status` *(R-01)*.
  - the function counts rows with `old.status = 0 AND new.status = 1` (join on `id, op_date`); if > 0, it runs `REFRESH MATERIALIZED VIEW CONCURRENTLY` and writes a log row.
  - The trigger, not the job, does the refresh, so *every* 0→1 update is covered, including manual ones *(R-09)*.
- Spike already confirmed: works on a partitioned root, `CONCURRENTLY` works inside the trigger, sees own transaction's changes, no-op updates are skipped *(R-05)*.
- **Verify:** MV totals == live `SELECT … WHERE status = 1` after job runs; `mv_refresh_log` rows match `confirm_job_log` runs with `rows_confirmed > 0`.

### Stage 7 — Replication (requirement 7)
- Primary: role `replicator` (`LOGIN REPLICATION`, password from `.env`), `GRANT USAGE ON SCHEMA ops`, `GRANT SELECT ON ops.operations`; `CREATE PUBLICATION ops_pub FOR TABLE ops.operations WITH (publish_via_partition_root = true)`. No `pg_hba` change needed *(R-07)*.
- Replica: the same common DDL, which already **pre-creates partitions covering the publisher's data range before subscribing** *(R-03)* and schedules the partition-maintenance job (moved to `common/02` in Stage 1); `CREATE SUBSCRIPTION ops_sub CONNECTION 'host=pg-primary … user=replicator' PUBLICATION ops_pub` (initial copy included).
- **Verify:** counts and `sum(amount)` per status match on both sides; a fresh row from the 5-s job and a status flip from the 3-s job appear on the replica within seconds; `DEFAULT` empty on the replica; `pg_stat_subscription`, `pg_replication_slots`.

### Stage 8 — Verification & README
- `verify/` — one script per requirement + `verify/run.ps1`/`run.sh` that runs all of them against both containers.
- Root `README.md`: quick start, requirement → object mapping, how to observe jobs / MV / replication.
- `docs/04-implementation-log.md` — what was done per stage, problems hit, deviations from the plan.

## Known limitations (to be documented, not solved)
- MV refresh is a full recomputation. That is fine for ~100k rows; for large volumes switch to an incrementally maintained summary table (D-08).
- Logical replication doesn't replicate DDL: schema changes must be applied to both sides. Partitions are handled independently on each side thanks to `publish_via_partition_root`.
- The GUID registry grows with T1; partition retention must also prune the registry (the composite FK enforces the order: detach/drop the partition first, then the registry rows).
- `pg_cron` interval jobs don't overlap with themselves; if a run takes longer than its interval, the next one waits.
